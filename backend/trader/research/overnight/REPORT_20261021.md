## 1. The finding that matters: `book_flow` is dead in live

The live loop's own log, every cycle:

```
WARNING live  scoring with features the row cannot supply — missing none, all-NaN
['imbalance_change_3','depth_trend_3','spread_change_3',
 'imbalance_persistence','mid_change_1','mid_change_3']
LightGBM will substitute its learned default, so this is a different model
from the one whose gates were measured.
```

Verified against the artifact: `models/forecast.joblib` has **55 features and
all six of those are among them**. So 11% of the deployed model's inputs are
NaN on every real-money decision, and have been since `book_flow` was enabled.

**Cause.** `book_flow_features` is called from exactly one place,
`core/dataset.py` — the research path. `livetrade/features.py`, the module
whose entire job is "the features `score_live` cannot build from bars", has no
reference to `book_flow`, `mid_change` or `imbalance_change_3` at all. The
group was wired into training and never into live.

Nothing else is affected: the warning says "missing none" for the other 49.

**The fix is nearly free, and I measured it** (ARM C below): retraining without
`book_flow` costs 0.00004 of log-loss skill — noise — and *improves* most money
gates, including `realised_edge_lcb` 4x. The alternative, implementing
`book_flow` live, needs minute-history of the book from the stream cache and is
a live-path change I would not make unattended.

This also hands [[project-backtest-live-gap]] a candidate cause nobody had tested.

## 3. The first comparison was invalid, and you caught why

`--quote-sources` is matched on the bare source name and applied to **both**
venues. Polymarket's observers are also called `backfill`, `live` and
`live_touch`, so naming Kalshi's live sources also discarded Polymarket's
gamma-API backfill — a different pipeline with none of the deci-cent
quantisation the restriction exists to avoid. Under `--complete-cases` every
row needing a `cross_venue` feature went with it:

```
6,465 candidate windows -> 956 windows / 5,894 rows
every fold under the 200-window minimum
ValueError: no fold had enough training windows
```

My first repair dropped `cross_venue` from both arms. That was wrong — it
answers a narrower question and discards a real feature group to dodge a filter
limitation. You pushed back and you were right.

**Proper fix: `peer_quote_sources`.** `attach_quotes(peer_sources=)`,
`Config.peer_quote_sources`, `--peer-quote-sources`. `None` follows
`--quote-sources` so nothing existing changes; `all` frees the peer. Same shape
as `peer_max_age_seconds` and `peer_null_age`, which exist for exactly this
reason — the peer is a cross-venue FEATURE, never the book we execute against.

Verified on real data, 2026-09-20 → 10-05, 17,088 candidate rows:

| | Kalshi priced | peer | both | windows |
|---|---|---|---|---|
| all sources | 17,088 | 5,022 | 5,022 | 2,845 |
| kalshi-only, shared filter | 17,073 | **361** | 361 | 341 |
| kalshi-only, peer freed | 17,073 | 5,022 | 5,017 | 2,844 |

The collapse was **entirely** the peer: Kalshi lost 15 rows of 17,088.

Side note worth its own experiment: peer coverage is only 29%, and
`--complete-cases` requires `cross_venue` non-null — so every arm is discarding
~71% of its rows to keep Polymarket features.

## 4. Data collection

**Tape (`venue_trades`)** — the dataset the maker thesis depends on, 6% full at
the start of the night.

* `TAPE_MAX_PAGES` (default 150) + `KalshiClient.market_trades(max_pages=)`.
  The old 40-page cap truncated busy markets at 40,000 prints, and a truncated
  tape is not a short one — the missing rows are the prints that would have hit
  a resting order. Truncations went **11 → 0**.
* Retuned to `--concurrency 2`: the 429 retry holds its semaphore slot while it
  sleeps 2/4/8/16/32s, so once 429s start throughput collapses. Measured
  **~11 markets/min at concurrency 4 vs ~96/min at 2** — about 9x.
* Running clean, 0 failed, 0 empty, `taker_book_side` populated and balanced.

**Candles (`venue_candles`, new dataset)** — we were discarding most of the
payload. The venue sends, per minute:

```
open_interest_fp, volume_fp
price   {open,high,low,close,mean,previous}   <- TRADED prints
yes_bid {open,high,low,close}                 <- the quote
yes_ask {open,high,low,close}
```

Only `yes_bid.close`/`yes_ask.close` were kept. **`price_low` is the valuable
one**: the cheapest print inside the minute, so a `price_low` at or below a
resting bid is evidence that bid would have filled — a cheap bound on the maker
question over every market the endpoint serves, where the tape must be
backfilled market by market. It is a bound, not the tape: a candle cannot say
which side crossed, so `taker_book_side` is still needed for the exact answer.

Kept as its own dataset, deliberately — `venue_depth` is a book summary and the
live writers depend on its schema, so nothing here can disturb a running loop.

**Candle backfill chunk bug** — the loop logged `"split it"` and then
`continue`d, silently dropping every window in an oversized chunk, and chunks
overflow precisely when they are dense. Demonstrated: on a 56-window input the
old loop requested **0**, the new planner requests all 56.

**Ladder replay** — the Oct 14–18 minute grid is repaired, 4-of-15 → ~16-of-16.
Correction to something I said earlier: the replay bought *precision*, not
*sample*. Its 1,747 windows sit inside the span candlesticks already cover; what
changed is that they are now priced by the true-tick replayed book instead of
candle OHLC.


Note what is NOT in that list: `deployed_residual_scale`. The walk-forward
scored 0.940 and the all-data refit shipped 0.015 — which is exactly the

**A correction to my own first reading of this.** `deployed_residual_scale`
reads `nan` in all three arms and I nearly reported that as a gate that cannot
catch its own case. It is not. The value is set only in `scripts/promote.py`,
after `refit_on_all` and `choose_candidate`; `scripts.evaluate` never builds a
deployed artifact, so `nan` there is correct and carries no information. The
gate works, at promotion, which is where it belongs — and it will be live the
next time anything is promoted.

**So the live model today is doubly attenuated**: 6 of 55 features NaN

### Two bugs of my own, found by running the thing

* **`_flush` lost `pd`.** Extracting it to module scope broke it: this script
  imports pandas lazily inside `run()`, so a module-level helper cannot see the
  name. It died with `NameError` only after the tape had finished and the
  chained job started — every existing test passed because none of them
  exercised `_flush`. Fixed, plus three tests that do.
* **The chained job's liveness probe self-matched.** It iterated
  `/proc/[0-9]*`, so `[ "$p" = "/proc/self" ]` never matched and the probing
  shell — whose own cmdline contains the pattern it greps for — counted itself.
  The probe could never have reported "finished", so the candles would never
  have started. Excluding `$$` fixes it; verified it now reads 1 real process
  rather than 2.
